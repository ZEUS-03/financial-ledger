# Assumptions and design choices

The assessment specifies behavior, not routes, a currency, decimal precision, exact error codes, a framework, or a duplicate-success status. These choices are implementation decisions:

1. All accounts use one implicit currency with two decimal places. Currency conversion and multiple currencies are out of scope. Monetary JSON inputs can be decimal strings or numbers; strings are preferred. Decimal strings allow at most two fractional digits and no exponent. Numeric JSON tokens are validated from their original source text before floating-point rounding can hide invalid precision or overflow. Numeric exponent/trailing-zero forms are accepted only when their exact value is a positive multiple of 0.01 within `10000000000.00` (for example `1e-2`, `1.2300`, and `1.234e1`). Responses always contain fixed two-place strings.
2. Amounts are converted to integer minor units with `BigInt` parsing, then stored within a safe integer range. Account balances cannot exceed the same maximum. An attempted overflow returns 409 without creating a transaction.
3. Account and transaction IDs are system-generated UUID v4 values; API account IDs must be lowercase UUID v4. The internal monotonically increasing transaction sequence is not exposed. Timestamps are UTC ISO strings generated by SQLite.
4. A nonblank account name is required, trimmed, and limited to 200 characters. Names need not be unique. Clients cannot set account ID, timestamp, or initial balance: such fields produce a validation error rather than being silently ignored.
5. A reference is a case-sensitive string of 1-128 characters, without leading/trailing whitespace. Description is optional, defaults to the empty string and is limited to 1000 characters. Unknown request fields are rejected. Whitespace inside a description is preserved.
6. Duplicate identity is `(account_id, reference_id)`. If type, amount and description match the persisted standalone transaction, return its unchanged data, HTTP 200 and `meta.replayed=true`. Numerically equivalent amounts such as `"1"` and `"1.00"` match. A changed payload produces 409. Failed requests do not reserve their reference. A replay is checked before checking current funds, so retrying a successful debit still works when the account is now empty.
7. Transfer identity is `(source_account_id, reference_id)`. Identical destination, amount and description replay the original transfer. Both ledger legs use that same reference in their respective accounts. Therefore a reference already used in either account blocks a new transfer, including a destination-only collision; the whole transfer rolls back. Standalone calls cannot replay transfer legs. Self-transfers are rejected.
8. Default history page is 1 and limit is 20; limit is capped at 100 and page at 1,000,000. Invalid, unknown and repeated query parameters return 400. A page beyond the last returns an empty list with accurate totals. An empty account has zero total pages. Type filtering affects both rows and total count.
9. History uses `created_at DESC` with insertion sequence descending to break timestamp ties. Rows and count are consistent within one response. Offset pages are not a snapshot across separate requests, so new concurrent entries may shift rows between page requests. Cursor pagination is optional, not an assessment requirement. The system clock is assumed to be maintained correctly.
10. Missing well-formed account IDs return 404; malformed IDs return 400. Validation and malformed JSON use 400; insufficient balance, amount overflow and reference conflicts use 409. These exact statuses are chosen conventions, not exact codes dictated by the assessment.
11. Immutability is enforced in the API and by SQLite triggers. Database administrators can still alter the schema, disable protections or change balances directly. The database file and administrative access must be trusted. There is no manual balance-adjustment API; corrections require new ledger entries.
12. One local SQLite file is the authority. Connections on the same host may share it with the same schema and pragmas. Network filesystems, cross-host replication, high availability, sustained high write concurrency and external payment integration are outside the implemented deployment scope.
13. No frontend, authentication system, user ownership, rate limiter, Docker deployment or cloud service is required by the assessment. A simple optional shared Bearer key, a public health check, request limits and timeouts were added as operational conveniences. They do not create tenant isolation.
14. Automated tests are requested by the user as a quality gate; the PDF does not separately mandate a specific framework, coverage percentage or test command. Tests are local verification and do not prove crash durability or production throughput.
15. Persisted text must be well-formed Unicode without NUL characters. NUL and unpaired surrogate values are rejected with 400 before SQLite can truncate or replace them. Request bodies must be valid UTF-8; malformed bytes return 400. Non-UTF-8 charset declarations and compressed content encodings return 415. These are input-integrity choices, not extra assessment features. Length limits count JavaScript UTF-16 code units; an emoji can count as two units. Reference strings use exact identity without Unicode normalization.
